# 真实工业表格任务合成方案

> 更新时间：2026-06-18
> 目标：为 TableClaw / 通用 TableAgent 第二阶段构建一批更真实、更难、可自动验证的表格任务，而不是继续依赖少量人工 gold case。

## 1. 背景

当前 TableClaw 已经在四川财资工业表格上形成第一阶段闭环：

- 有真实工业表格；
- 有 `workspace/uploads/` 多表工作区；
- 有 schema cache、table index、domain pack、表格读算工具和并行评测；
- 有 badcase122 与 query100 variants 的稳定回归结果。

但如果继续向通用 TableAgent / 论文方向推进，只靠人工写题会遇到几个问题：

- gold answer 成本高，且容易出现题面和答案口径不一致；
- LLM judge 难免需要放宽格式/小数/图表展示，容易让评测可信度被质疑；
- 手写任务容易过拟合当前四川财资口径；
- 缺少系统化难度控制，难以证明具体机制解决了哪类错误；
- 开放式报告/图表任务很难直接给唯一标准答案。

因此，第二阶段应从“人工写问答”转向：

```text
真实表格
-> 自动 profiling
-> 任务反向合成
-> 程序化 gold / verifier
-> 表格结构扰动
-> 分层评测与错误归因
```

核心思想是：不要从“自然语言问题”开始造数据，而是先构造一个可验证的表格世界，再从这个表格世界反向生成任务。

## 2. 核心 Insight

表格 Agent 的评测不应该只依赖自然语言题目和人工答案，而应该依赖可执行的表格状态。

更具体地说：

> 先让程序知道某张表里有哪些实体、时间、指标、单位和公式，再由程序生成问题并计算 gold answer。这样任务可以真实、复杂，同时答案可复现、可审计。

这和普通 QA 数据集不同。TableAgent 的关键能力不是背答案，而是：

- 找到正确的 workbook / sheet；
- 对齐多行表头和指标组；
- 理解实体、时间、单位、百分比编码；
- 执行排序、筛选、比较、趋势和公式校验；
- 输出可验证的底层数据和证据链。

所以评测数据也应该围绕这些能力生成。

## 3. 数据合成总体流程

建议采用五阶段流水线。

```text
真实表格池
  ↓
Table Profiler
  ↓
Task Generator
  ↓
Deterministic Verifier
  ↓
Perturbation Engine
  ↓
Benchmark Splits
```

### 3.1 真实表格池

输入是真实业务表格，而不是纯合成表格。

可以使用：

- 当前 `test_table/` 中的工业表格；
- `workspace/uploads/` 中已模拟上传的表格；
- 后续新增的其他行业/客户表格；
- 人工脱敏后的真实 Excel / CSV。

真实表格的价值在于它天然包含：

- 多 sheet；
- 合并单元格；
- 多级表头；
- 横向月份展开；
- 合计行；
- 空值和稀疏字段；
- 单位混杂；
- 业务指标简称；
- 公式或排名列。

这些复杂性很难靠从零合成表格模拟出来。

### 3.2 Table Profiler

Profiler 负责把一张表解析成结构化描述。

输出可以类似：

```json
{
  "table_id": "tbl_xxx",
  "path": "workspace/uploads/xxx.xlsx",
  "sheets": [
    {
      "sheet": "Sheet1",
      "header_rows": [1, 2],
      "entity_columns": ["单位", "市州", "省份"],
      "time_columns": ["202501", "202502"],
      "metric_columns": [
        {
          "name": "应收总额同比增幅",
          "unit": "%",
          "value_type": "change",
          "header_path": ["应收总额情况", "应收总额同比增幅"]
        }
      ],
      "summary_row_patterns": ["合计", "市州合计", "汇总"],
      "has_merged_cells": true
    }
  ]
}
```

当前 TableClaw 已有相近基础：

- `tableclaw_inspect`
- `workspace/table_cache/*.schema.json`
- `tableclaw_retrieve_tables`
- `workspace/table_index/tables.jsonl`

第二阶段可以在这些基础上发展出更标准的 `table_profile.json`。

### 3.3 Task Generator

Task Generator 根据 profiler 自动生成任务。

任务不应只覆盖问答，还应覆盖表格上下游 workflow。

推荐先支持以下类型：

| 类型 | 示例 | Gold 方式 |
| --- | --- | --- |
| schema_understanding | 这个表有哪些 sheet？哪个 sheet 是市州维度？ | profiler 直接给 |
| lookup_qa | 成都 202502 的营业收现率是多少？ | 精确查单元格 |
| topk_ranking | 202502 应收占收比最高的 3 个单位是谁？ | 程序排序 |
| filter_qa | 找出收入同比为负且应收占收比高于 10% 的单位 | 程序筛选 |
| compare_change | 成都从 202501 到 202502 变化了多少？ | 程序计算差值/增幅 |
| time_series | 四川 2025 年 1-6 月某指标趋势 | 程序抽序列 |
| chart_table | 生成图表底表：各单位两项指标对比 | 程序生成底表 |
| formula_validate | 检查占收比是否等于应收/收入 | 程序公式校验 |
| cleaning_transform | 删除合计行、统一单位、转换百分比 | expected diff / transformed table |

早期主评测建议先做：

```text
lookup_qa
topk_ranking
filter_qa
compare_change
time_series
chart_table
formula_validate
```

报告生成、开放式分析建议可以保留为 demo 或 secondary eval，不作为主 ACC。

### 3.4 Deterministic Verifier

每类任务都配一个确定性 verifier。

例如：

```text
lookup_verifier
topk_verifier
filter_verifier
series_verifier
chart_table_verifier
formula_verifier
transform_diff_verifier
```

Verifier 不依赖 LLM judge 来判断核心数值是否正确，而是直接比较结构化结果。

建议 gold task 存储：

```json
{
  "task_id": "task_001",
  "task_type": "topk_ranking",
  "difficulty": "medium",
  "question": "202502 营业收现率最高的 3 个单位是谁？",
  "gold_answer": [
    {"entity": "达州", "value": 1.0867},
    {"entity": "乐山", "value": 1.0428},
    {"entity": "巴中", "value": 1.0404}
  ],
  "gold_evidence": [
    {
      "file": "市州数据-营业收现率台账.xlsx",
      "sheet": "Sheet1",
      "entity_column": "单位",
      "metric_header": ["202602", "营业收现率完成"],
      "rows": [18, 12, 20],
      "columns": ["C"]
    }
  ]
}
```

这样不仅能评答案，还能评：

- 表是否找对；
- sheet 是否找对；
- 列是否找对；
- 行是否找对；
- 排序方向是否正确。

## 4. 难度设计

任务难度不要只靠把问题写得绕，而应该来自真实表格复杂性。

建议定义 5 个难度旋钮。

### 4.1 表格结构复杂度

从易到难：

1. 单 sheet、单行表头；
2. 多 sheet；
3. 多行表头；
4. 合并单元格；
5. 横向月份展开；
6. 指标组嵌套；
7. 空值、排名列、合计行混杂；
8. 多表/跨月/跨 sheet。

### 4.2 任务步骤数

从易到难：

1. 查单值；
2. 定位列 + 排序；
3. 筛选 + 计算；
4. 跨月/跨表 + cohort + 输出底表；
5. 读表 + 清洗 + 公式验证 + 报告。

### 4.3 语义模糊度

从易到难：

1. 使用表头原名；
2. 使用指标简称；
3. 使用同义词；
4. 使用业务口径；
5. 省略年份/月；
6. 使用多轮上下文，例如“还是刚才那个口径”。

### 4.4 证据缺失或冲突

从易到难：

1. 表内字段完整；
2. 有合计行干扰；
3. 有空值；
4. 有排名列但无数值；
5. 有两个近似指标；
6. domain memory 与表内证据冲突；
7. gold/reporting 口径与 raw table 不完全一致。

### 4.5 输出复杂度

从易到难：

1. 单值；
2. 列表；
3. 排名表；
4. chart-ready table；
5. 修改后的表格；
6. 带证据的报告；
7. 可回滚 diff。

## 5. 表格扰动策略

为了测试通用性，不能只在原始表上生成任务，还要对表做结构保持扰动。

### 5.1 数值扰动

保持表结构不变，修改底层数值：

```text
value' = value * random_factor
```

然后同步重算派生列：

```text
占收比 = 应收 / 收入
同比 = (本期 - 去年同期) / 去年同期
排名 = sort(...)
```

这样可以生成大量不同答案的任务，避免模型记忆固定数值。

### 5.2 实体扰动

替换实体名：

```text
成都 -> A市
绵阳 -> B市
广东 -> P省
```

或迁移到更通用实体：

```text
门店、产品、供应商、客户、项目、区域
```

这样可以减少四川财资实体过拟合。

### 5.3 表头扰动

进行同义词替换：

```text
应收总额 -> 应收账款合计
收入同比增幅 -> 营收同比增长率
占收比 -> 应收收入比
营业收现率 -> 现金回收率
```

gold 不变，但模型必须做指标归一化。

### 5.4 格式扰动

常见扰动包括：

- `0.123` 改成 `12.3%`；
- 万元改亿元；
- 插入空行；
- 插入合计行；
- 调换列顺序；
- 合并标题行；
- 拆分多个 sheet；
- 隐藏部分辅助列；
- 添加无关列。

这些扰动能测试 schema grounding 和工具鲁棒性。

### 5.5 任务改写扰动

对同一 gold 生成多种 query：

```text
请找出 2025 年 2 月应收占收比最高的 3 个单位。
202502 哪三个单位应收收入比最高？
2 月份这个指标 TOP3 是谁？
帮我列一下 2025 年 2 月风险最高的三个单位。
```

这能测试 query rewrite 泛化，而不是只测固定模板。

## 6. Gold 难题的处理策略

不是所有任务都适合唯一 gold。

建议分三类处理。

### 6.1 强确定任务

这些任务应作为主 ACC：

- lookup；
- topk；
- filter；
- compare；
- time series；
- chart data；
- formula validation；
- table transform diff。

它们都可以由程序给 gold。

### 6.2 半开放任务

例如业务总结、趋势解读，可以用 rubric：

```json
{
  "must_include": ["安徽应收增幅最高", "四川收入同比为负"],
  "must_not_include": ["湖北属于当前默认 200亿省"],
  "numeric_facts": [
    {"entity": "安徽", "metric": "应收增幅", "value": 79.7, "unit": "%"}
  ]
}
```

这类可以用 LLM judge + numeric checker 混合评。

### 6.3 开放任务

例如“写分析建议”“生成管理层报告”，不建议早期作为主指标。可以作为 demo 或人工评审集。

## 7. Benchmark 设计建议

建议构建一个多 split benchmark。

```text
TableClawBench/
├── tables/
│   ├── raw/
│   ├── perturbed_numeric/
│   ├── perturbed_schema/
│   └── perturbed_entity/
├── profiles/
├── tasks/
│   ├── train_like.jsonl
│   ├── seen_table_unseen_query.jsonl
│   ├── unseen_table_seen_task.jsonl
│   ├── unseen_table_unseen_query.jsonl
│   └── stress_conflict.jsonl
└── verifiers/
```

### 推荐 split

| Split | 目的 |
| --- | --- |
| seen_table_seen_template | 验证基础执行链路 |
| seen_table_unseen_query | 验证 query rewrite 泛化 |
| perturbed_table_same_task | 验证 schema/格式鲁棒性 |
| unseen_table_same_domain | 验证同领域新表泛化 |
| unseen_domain | 验证通用 TableAgent 能力 |
| conflict/sparse | 验证 memory-evidence reconciliation |

### 推荐指标

不要只看最终 ACC。

建议同时记录：

- final answer ACC；
- table retrieval Recall@1 / Recall@3；
- sheet grounding accuracy；
- column grounding accuracy；
- row/entity grounding accuracy；
- numeric exact / tolerance match；
- evidence completeness；
- tool steps；
- token cost；
- elapsed time；
- retry / failure rate；
- memory usage correctness。

这样才能知道改进来自哪里。

## 8. 和科研方向的关系

真实数据任务合成不仅服务工程，也能服务科研。

如果后续论文不只做 TableAgent，而是做更通用的 Agent memory / evidence / tool-use 研究，这套数据可以用于验证：

- schema memory 是否提升表召回；
- domain memory 是否提升业务口径稳定性；
- memory 是否会造成 overfitting；
- evidence-grounded workflow 是否减少 hallucination；
- lightweight state machine 是否减少跳步错误；
- memory-evidence reconciliation 是否能处理 sparse/conflict 表格。

尤其是 conflict/sparse split 可以直接支撑一个更通用的研究问题：

> 当当前工具证据与历史/领域 memory 冲突时，Agent 应该如何判断、信任和回退？

表格场景的好处是：证据链、数值、行列、公式都能被程序验证，因此比很多开放任务更适合做可靠 Agent 研究。

## 9. 最小可落地版本

第二阶段可以先做一个 MVP。

### MVP 输入

- 10-20 张真实工业表格；
- 先不做复杂表格编辑，只做读算类任务。

### MVP 支持任务

先支持 6 类：

1. lookup；
2. topk；
3. filter；
4. compare/change；
5. time_series；
6. chart_table。

### MVP 产出

每张表生成 20-50 个任务。

总计：

```text
10 张表 x 30 题 = 300 条
20 张表 x 30 题 = 600 条
```

再做 1-2 类扰动：

- 表头同义词扰动；
- 列顺序/合计行扰动。

就可以得到 600-1200 条可验证任务。

### MVP 工程模块

```text
eval_test/synthetic/
├── profile_tables.py
├── generate_tasks.py
├── perturb_tables.py
├── verify_answers.py
└── README.md
```

## 10. 开发优先级

建议按这个顺序推进：

1. **Profiler v0**
   复用 `tableclaw_inspect` / schema cache，导出 entity/time/metric columns。

2. **Task Generator v0**
   只生成 lookup、topk、filter、compare、chart_table。

3. **Verifier v0**
   用 pandas/openpyxl 确定性计算 gold。

4. **Evidence 标注**
   每条 gold 附 file/sheet/row/column/header_path。

5. **Query Rewrite**
   同一 task 生成 3-5 种自然语言表达。

6. **Perturbation v0**
   做表头同义词和列顺序扰动。

7. **Baseline Eval**
   跑当前 TableClaw，记录 table recall、column grounding、answer ACC。

8. **Ablation**
   关 schema index、关 domain knowledge、关 memory/skill，看各层贡献。

## 11. 风险与注意事项

- 不要让合成任务过度模板化，否则只能证明程序会出题，不能证明 Agent 真懂复杂表格。
- 不要一开始就评开放式报告，否则 gold 不稳定。
- 不要只用四川财资实体，否则容易被质疑过拟合。
- 不要只看最终 ACC，要看 grounding 和 evidence。
- 不要把扰动做得不符合真实业务表格习惯，否则 benchmark 会变成玩具。
- 人工抽检仍然需要保留，建议每批抽检 5%-10%。

## 12. 总结

真实工业表格任务合成的关键不是“让 LLM 编几道题”，而是：

```text
真实表格结构
+ 程序化任务生成
+ 确定性 verifier
+ 可控扰动
+ evidence 标注
+ 多 split 泛化评测
```

这条路线能同时服务三个目标：

1. 工程上：持续获得更稳定、更大规模的回归集；
2. 产品上：覆盖表格问答、图表底表、筛选、趋势、校验等真实工作流；
3. 科研上：为 memory、schema retrieval、tool evidence、workflow state machine 和 memory-evidence reconciliation 提供可验证实验场。

最短路径不是继续人工写 gold，而是先做一个可运行的 `Profiler + Generator + Verifier` MVP。
